# 多模态可靠任务 200 文件压测报告

## 一、结论

2026 年 8 月 12 日使用 50 个视频、100 张图片和 50 个文本文件完成真实 PostgreSQL 与 Redis 压测。
三类文件全部先创建耐久任务，再由独立资源池资产化并写入数据库。

最终 200 个任务全部一次成功，生成 1,064 个资产。三个 Redis 路由的待确认消息、延迟消息、死信和隔离
消息均为 0；内容理解、模型调用、向量和聚类记录均为 0。测试通过。

## 二、测试范围

本次包含：

- PostgreSQL 作业、源文件、任务和资产写入；
- Redis 三路任务投递与确认；
- 视频真实探测、画面分析和逻辑分段；
- 图片整图资产化；
- 文本解析、父子分块和资产化；
- 租约、进展更新、任务收口和父作业计数。

本次不包含：

- 内容理解；
- 外部模型调用；
- 文本或多模态向量；
- Milvus 写入；
- 聚类。

测试数据保留在工作区 `bench_mixed_tasks_20260812_06f960c692`，便于复核数据库结果。

## 八、压测中发现并修复的问题

正式压测前的高并发回归发现两类只在多处理器同时领取时出现的问题：

1. ORM 更新语句的返回列在并发适配时可能错位，导致任务类型或工作进程编号被读成整数；
2. 图片整批提交已经成功更新任务，但对返回值的解释可能误判为父作业变化。

修复方式不是增加重试掩盖问题，而是收紧事务协议：

- 领取只检查受影响行数是否恰好为 1；
- 租约身份由已验证消息、服务端处理进程编号和本次随机令牌构造；
- 所有围栏参数使用固定名称、固定类型和固定顺序；
- 父作业计数使用事务中已加锁任务的父作业编号；
- 结果提交只检查更新行数，不读取易错位的返回列。

相同的 35 文件高并发回归随后连续通过，正式 200 文件压测也实现 200/200 一次成功。

## 九、结论与建议

当前建议保留视频并发 2。图片并发 16、文本并发 4 在本机测试中没有造成视频资源争抢，也没有产生
数据库积压或队列残留。

报告可以重点使用四项最能体现改造价值的指标：

1. 200 个混合任务一次成功率为 100%；
2. 1,064 个资产原子入库，重复和数量不一致均为 0；
3. 三路队列最终积压、延迟、死信和隔离均为 0；
4. 内容理解、模型、向量和聚类调用均为 0，证明阶段隔离有效。

浏览器文件夹导入现已默认接入耐久任务：一个上传作业下挂多个视频、图片和文本任务，前端看到的作业计数
和进度仍以文件数为单位。完成请求返回前，数据库会在同一事务中启动作业、建立完整任务批次并登记分发；
Redis 初次投递失败由各路由调度进程恢复，不会留下依赖接口进程内存状态的半完成作业。
